Payroll tax API effective dating

Rules belong to a date. The check date chooses which.

Tax rules are not timeless. Wage bases, brackets and rates change each January, and some change mid-year. A payroll tax API that holds only today's rules gives wrong answers for yesterday's paycheck. Omnia.tax holds rules by effective date and lets the checkDate on the request choose.

Why the check date, not the pay period

Payroll tax follows when wages are paid, not when they were earned. A paycheck dated 2026-01-02 for work done in December 2025 is taxed under 2026 rules. So the request carries checkDate and nothing else decides the year.

Corrections and back pay

A correction to an earlier year's paycheck must use that year's tables. Send the original check date and the engine applies that year's rules. A run in the next year for last year's pay does not silently use new numbers.

A year without rules

If the check date falls in a year the engine has no rules for, the API returns 422 with the code unsupported_tax_year instead of guessing. GET /v1/states?year=2027 lists which states have rules for a given year. Years that are provisional carry a note in warnings.

Mid-year changes

When a state revises a formula during the year, the rule file carries an effective date, so checks dated before it keep the old method and checks after it use the new one. The changelog records the changes.

Questions

Which year does the API use for a paycheck?

The year of the checkDate on the request. The pay period dates do not decide it.

Can I run a correction for last year?

Yes. Send the original check date and the engine applies that year's rules, so the correction ties to what should have been withheld then.

What happens if there are no rules for the year?

The API returns 422 with unsupported_tax_year rather than using another year's numbers.
