Payroll tax API: money in integer cents

Why every amount is a whole number, and where rounding happens.

Payroll amounts must tie to the penny. Withheld tax is deposited and reported, and a one-cent difference per paycheck becomes a reconciliation problem across thousands of them. The Omnia.tax API therefore uses integer cents for every amount, in requests and responses.

The floating-point problem

In most programming languages 0.1 + 0.2 is not 0.3. Add enough dollar amounts stored as floating point and totals drift by fractions of a cent, which then round the wrong way on one line. Integers do not drift. $3,000.00 is 300000, and 300000 plus 300000 is exactly 600000.

What the API does

  • Requests must send whole cents. 3000.5 is refused with a message showing what to send instead.
  • Responses return whole cents in every amount field.
  • Rounding happens once per tax, at the point that tax's amount is produced from its base and rate. Nothing accumulates a fraction.
  • Totals are sums of integers, so employeeTaxTotal equals the sum of the employee lines exactly.

Check it yourself

In the Columbus example the employee lines add up to $700.65 and employeeTaxTotal is $700.65. They match because there is nothing to disagree about.

On your side

  • Store amounts as integer cents in your database.
  • Convert to dollars only for display, and format with a currency formatter.
  • If you receive dollars from a form, convert with rounding at the edge: Math.round(dollars * 100), then never touch floats again.

Questions

Why does the API use cents instead of dollars?

Integers add exactly. Dollar amounts stored as floating point drift by fractions of a cent, which can round the wrong way and break reconciliation to deposits.

What happens if I send a decimal amount?

The request is refused with a 422 invalid_input error that names the field and shows the whole-cent value to send.
