Migrating from a Symmetry-style payCalc integration

The request shape looks familiar. The ids and contract are not the same.

If your product already calls a Symmetry-style payCalc, you may want to try Omnia.tax without rewriting everything. Omnia.tax has an adapter that accepts a Symmetry-shaped request, which makes the first experiment cheap. It is not a drop-in replacement, and this page says exactly where it differs.

What the adapter does

  • Accepts an array of payCalc requests at POST /v1/payCalc and returns an array of results.
  • Uses the vocabulary a Symmetry integration expects: payCalc, UniqueTaxId, LocationCode, TaxJurisdictionParms.
  • Calculates with the same engine as POST /v1/paycheck.

What it does not do

  • It is not wire-compatible with the Symmetry Tax Engine API.
  • Its jurisdiction ids are Omnia.tax's own, generated from its own sourced rule files. They do not match Symmetry's numbers for the same place and must not be sent to a Symmetry integration.
  • It does not reproduce Symmetry's proprietary id catalog.

A migration plan

  • Map each employee to the Omnia.tax request: earnings, deductions, the W-4, year-to-date wages and the work-state certificate.
  • Resolve addresses with POST /v1/address to get the certificate fields instead of mapping ids by hand.
  • Run twenty real paychecks through both and compare line by line.
  • Plan to change the integration; budget for it.

Questions

Is Omnia.tax compatible with the Symmetry Tax Engine API?

No. It has an adapter that accepts a Symmetry-shaped payCalc request, but it is not wire-compatible and its jurisdiction ids are its own. Expect to change your integration.

Can I try it with my existing request shape?

The adapter makes a first experiment cheaper, but the results use Omnia.tax ids, so plan a real mapping before production.
