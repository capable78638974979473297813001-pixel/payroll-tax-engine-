Omnia API reference

Gross-to-net US payroll tax calculation for all 50 states, DC, and the municipal, county and school-district lines underneath them — one authenticated request per paycheck.

Omnia is payroll-tax infrastructure, not a payroll app. You send the facts of a single paycheck — earnings, deductions, the employee's W-4, year-to-date wages, and where the work happens — and Omnia returns every tax line that applies, for both the employee and the employer, computed against the ruleset in effect on the check date.

The API is deliberately small. There is one calculation endpoint you call on every pay run, plus two read-only helpers. There are no SDKs to install and no per-jurisdiction feature flags: every state, DC, and every local jurisdiction Omnia knows about is included for every key.

Base URL

All endpoints are served over HTTPS from your Omnia host. The hosted service is:

https://api.omnia.tax

Self-hosted deployments run the same server on their own domain — swap the host and every path below is identical.

Your first call 
# One paycheck, federal + Ohio, biweekly
curl https://api.omnia.tax/api/paycheck \
  -H "Authorization: Bearer sk_test_…" \
  -H "Content-Type: application/json" \
  -d '{
    "checkDate": "2026-06-15",
    "payFrequency": "biweekly",
    "earnings": [
      { "code": "REG", "category": "regular",
        "amount": 300000 }
    ],
    "deductions": [],
    "federalW4": {
      "filingStatus": "single",
      "multipleJobs": false,
      "dependentCredit": 0,

Authentication

Every request to a calculation or account endpoint must carry an API key in the Authorization header as a bearer token:

Authorization: Bearer sk_test_a1b2c3…

Keys are issued from the Omnia console. Sign in, then click Issue my evaluation key — the plaintext key is shown once, so copy it immediately. Omnia stores only a SHA-256 hash of the key; it can never be recovered or re-displayed, only replaced.

Key lifecycle

  • One active key per account. Reissuing generates a fresh key and immediately revokes the previous one.
  • Evaluation keys expire. Keys minted during the free trial are time-boxed; the response tells you the exact expiresAt. An expired key returns 401.
  • Keep it server-side. A key can run any calculation on your account and is billable. Never ship it in a browser, mobile app, or public repository.
Test vs. live. Evaluation keys are prefixed sk_test_. Production keys are prefixed sk_live_. The two behave identically at the API; only billing and expiry differ.

Making requests

Requests and responses are JSON. Send Content-Type: application/json on any request with a body. The API is stateless: each call is a self-contained calculation, so you can fan out a whole pay run in parallel — one request per employee.

  • Idempotent by construction. The same input on the same checkDate always yields the same result — there is no server-side state that a call mutates (aside from usage metering).
  • No hidden defaults that move money. Every eligibility fact the engine can't derive — SUI rate, nexus, reciprocity election — is an explicit input. Omit an optional block and the rules that depend on it simply don't fire.
Request 
curl https://api.omnia.tax/api/paycheck \
  -H "Authorization: Bearer $OMNIA_KEY" \
  -H "Content-Type: application/json" \
  -d @paycheck.json

Money & rounding

Every monetary value in the API is an integer number of cents. There are no floating-point dollars anywhere in a request or response. 300000 means $3,000.00; a net pay of 246118 is $2,461.18.

This is deliberate: floating-point dollars silently lose pennies over a year of pay runs, and pennies are the whole game in payroll. Convert to and from dollars only at your display edge.

  • Withholding is computed to the cent. Set roundToWholeDollars: true on the input to round federal withholding to whole dollars, as IRS Pub 15-T permits.
  • Percentages that are inputs (an SUI rate, for example) are given as decimals — 0.031 for 3.1%.
Cents ↔ dollars
300000  // $3,000.00 gross
24000   // $240.00  401(k)
18600   // $186.00  Social Security
-246118 // never — amounts are unsigned

// display edge only:
dollars = cents / 100

Errors

Omnia uses conventional HTTP status codes. Every non-2xx response is a JSON error envelope with a stable machine-readable code, a human-readable error, and a requestId you can quote to support. A 200 wraps the payload under result.

200 OK 400 Bad request 401 Unauthorized 402 Payment required 422 Unprocessable 429 Too many requests
StatuscodeWhen it happens
200—The calculation ran; the body is { "result": … }.
400invalid_jsonThe body wasn't valid JSON.
401missing_key · invalid_key · expired_keyNo key, an unknown/inactive key, or an expired evaluation key.
402account_suspendedA billing issue (failed invoice) paused the account. A paid invoice reactivates it.
422invalid_inputValid JSON, but a field failed validation — see the details array.
422calculation_errorThe input validated but the engine could not complete the calculation.
429rate_limitedThe per-key rate limit was exceeded. Respect the Retry-After header.
Validation errors are precise. A 422 invalid_input carries a details array — one entry per bad field, each with a dotted path and a message — so you can point the operator at exactly what to fix rather than at a generic failure.

Rate limits

Each API key is rate-limited independently, on a fixed one-minute window. The default is 120 requests per minute per key; self-hosted deployments set their own via the RATE_LIMIT_PER_MIN environment variable.

Every calculation response carries the current budget in standard headers, so you can pace a large pay run without guessing:

HeaderMeaning
RateLimit-LimitRequests allowed in the window.
RateLimit-RemainingRequests left in the current window.
RateLimit-ResetUnix time (seconds) when the window resets.
Retry-AfterOn a 429 only: seconds to wait before retrying.

Over the limit you get a 429 with code: "rate_limited". Back off until Retry-After elapses; a fan-out pay run should cap its own concurrency rather than sprint into the limit.

Response headers
HTTP 200
RateLimit-Limit: 120
RateLimit-Remaining: 117
RateLimit-Reset: 1750000060
X-Request-Id: req_9f3a1c…
X-Omnia-Version: 1.0.0
Simple backoff — TS
async function withRetry(call) {
  for (;;) {
    const res = await call();
    if (res.status !== 429) return res;
    const s = Number(res.headers.get("retry-after")) || 1;
    await new Promise((r) => setTimeout(r, s * 1000));
  }
}

Calculate a paycheck

POST/api/paycheck

The core of the API. Send the facts of one paycheck and receive every applicable tax line — federal, state, and local, employee-side and employer-side — plus the gross-to-net summary. Requires a bearer key.

Request body — PaycheckInput

checkDatestringrequired
The pay date, ISO YYYY-MM-DD. This — not "today" — selects the ruleset. A recalculation of a prior period must use that period's date so it reproduces that period's rules.
payFrequencyenumrequired
How often this employee is paid. Determines the annualization factor.
weeklybiweeklysemimonthlymonthlyquarterlysemiannualannualdaily
earningsEarning[]required
One or more line items of pay. See Earning. At least one is required.
deductionsDeduction[]required
Pre-tax and post-tax deductions. See Deduction. Send [] if there are none.
federalW4FederalW4required
The employee's Form W-4 (2020 revision or later). See FederalW4.
ytdYearToDaterequired
Year-to-date wages, needed for every wage-base-capped tax (Social Security, FUTA, SUI…). See YearToDate.
workStateStateWithholdingoptional
Where the work is performed — whose state income tax runs. Omit for a federal-only calculation. See StateWithholding.
residenceStateStateWithholdingoptional
Where the employee lives. Set it whenever it differs from workState; omitting it means every residence-based rule (reciprocity, nonresident allocation, resident credits) simply doesn't fire.
residenceStateWithholdingobjectoptional
Whether to withhold the residence state's tax when there's no reciprocity — { nexus?, voluntary? }. Both are legal/business facts only you know. Ignored when reciprocity already governs the period.
employerEmployerContextoptional
Employer-side facts the engine can't derive — most importantly your assigned SUI/SUTA rate per state, e.g. { "stateUnemploymentRate": { "OH": 0.031 } }. Absent, the state's published new-employer rate is used and noted in the line's detail.
employmentCategoryenumoptional
Which employment-tax rules apply. Defaults to standard.
standardclergystatutory_employeehouseholdagriculturalrailroadelection_worker
priorRegularPaymentobjectoptional
For states that tax a stand-alone bonus by aggregating it with the last regular check — { taxableWages, stateIncomeTaxWithheld? }. Omit (the normal case) and the bonus is taxed on its own.
roundToWholeDollarsbooleanoptional
Round federal withholding to whole dollars, as IRS permits. Defaults to false (compute to the cent).

Health check

GET/api/health

An unauthenticated liveness and readiness probe, safe to hit from a load balancer or uptime monitor. It reports the running API version and how many jurisdictions this build can compute — so a probe also catches a bad deploy that shipped without its tax data.

Returns 200 when healthy, or 503 with status: "degraded" if the ruleset data can't be read. Also reachable at /healthz.

The PaycheckInput object

The complete request body for POST /api/paycheck. See the endpoint above for the field-by-field table. In brief:

  • Required: checkDate, payFrequency, earnings, deductions, federalW4, ytd.
  • Optional: workState, residenceState, residenceStateWithholding, employer, employmentCategory, priorRegularPayment, roundToWholeDollars.

The guiding convention: absent input changes nothing. Leave out an optional block and the rules that read it don't fire — no silent defaults that would move a dollar you didn't ask to move.

Type
interface PaycheckInput {
  checkDate: string;   // YYYY-MM-DD
  payFrequency: PayFrequency;
  earnings: Earning[];
  deductions: Deduction[];
  federalW4: FederalW4;
  ytd: YearToDate;
  workState?: StateWithholding;
  residenceState?: StateWithholding;
  residenceStateWithholding?: {
    nexus?: boolean;
    voluntary?: boolean;
  };
  employer?: EmployerContext;
  employmentCategory?: string;
  priorRegularPayment?: {
    taxableWages: number;
    stateIncomeTaxWithheld?: number;
  };
  roundToWholeDollars?: boolean;
}

Pricing

Usage-based, not per-employee-per-month. Every jurisdiction is included for everyone; you pay for the calculations you actually make. One POST /api/paycheck is one billable call, and the graduated bands mean a bigger book pays less per call.

Calls / yearRate per call
First 25,000$0.12
25,001 – 200,000$0.09
200,001 – 1,000,000$0.06
1,000,000+$0.04
  • Rooftop address resolution (when a local tax turns on a precise address) is billed at $0.30 per address, once per address — not once per pay run.
  • Free trial: a 14-day evaluation window before a card is needed. Evaluation keys (sk_test_) run the full engine.
  • Only 200 responses that ran a calculation are billable; auth failures and malformed requests are not.

Versioning & dates

Omnia is effective-dated. The ruleset that runs is the one in force on your checkDate — never "today's" rules. This is the single most important thing to get right when you integrate:

  • Recalculating a prior period (a correction, a void-and-reissue) reproduces that period's numbers because you send that period's checkDate.
  • Running next year's first payroll automatically picks up the new year's brackets, wage bases and local rates as soon as the check date crosses into the new year.

New jurisdictions and rate changes ship as data, not as breaking API changes. The request and response shapes on this page are stable; a new local tax appears as an additional TaxLine in the response, nothing more.
