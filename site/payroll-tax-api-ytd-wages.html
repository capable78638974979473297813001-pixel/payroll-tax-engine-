Payroll tax API year-to-date wages

Why each call carries the year so far, and what happens at the caps.

Some payroll taxes stop partway through the year, and one starts partway through. To know where a paycheck sits against those lines, the engine needs to know what the employee has been paid so far. Omnia.tax is stateless, so you send that on every call in the ytd object.

The fields

FieldUsed for
ytd.socialSecurityWages already subject to Social Security this year, against the $184,500 wage base in 2026.
ytd.medicareMedicare wages so far, which decide when Additional Medicare tax starts at $200,000.
ytd.futaWages already counted for federal unemployment tax.

A paycheck at the cap

An employee paid $10,000.00 in a check, with $180,500.00 already counted this year, has only $4,000.00 left under the $184,500.00 base. The engine taxes just that part:

TaxTaxable wagesAmount
Social Security$4,000.00$248.00
Social Security (Employer)$4,000.00$248.00
Medicare$10,000.00$145.00

With no year-to-date wages the same check would owe Social Security of $620.00; at the cap it owes $248.00. Medicare has no cap, so it is unchanged at $145.00.

Why it is on every request

Stateless calls mean a retry or a replay for an audit returns the identical answer, and nothing in the service can drift from your books. The cost is that your payroll system is the record of year-to-date wages, which it already is.

Getting it right

  • Start the year at zero on the first check dated in that year.
  • Add the wages from each check you have run, per the tax: Social Security wages exclude section 125 premiums, for example.
  • When an employee joins mid-year from another employer, only wages from your payroll count toward your caps unless the law says otherwise.

Questions

Why does the API need year-to-date wages?

Social Security stops at a wage base and Additional Medicare starts above a threshold. Knowing the year so far lets the engine tax only the part of a check that is still under or over the line.

Does the API store year-to-date totals?

No. Calls are stateless. You send the year-to-date figures with each request, so a replay returns the same answer.
